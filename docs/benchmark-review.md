# 1. Understand the environment

I selected **HealthAgentBench `clinical_trial_matching_task_19`**, a clinical-document task rather than an imaging task. It asks the agent to identify every eligible trial for one patient and exclude unrelated or ineligible trials. Its explicit output makes the difference between the requested work and the rewarded work easy to inspect.

The review uses HealthAgentBench commit `bcbb8085fd549469e2dc7455f4bfd68a1b98895a`. I inspected the task, container configuration, bootstrap and evaluator. I also ran six controlled inputs through the copied evaluator. **I did not run the full benchmark harness, evaluate an agent, or independently adjudicate the clinical labels.**

## The episode contract

| Element                  | What the inspected implementation establishes                                                                                                                                                                                                  | What remains to be tested                                                                                                                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Observation              | The agent receives the task instruction and reads `/workspace/data/topic.txt`, the patient case; `topic_id.txt`; and candidate trial XML files in `trials/`. The pinned pool contains 301 trial IDs and the gold file contains four.           | Whether all staged documents are complete and clinically consistent with the reference labels.                                                                                                 |
| Actions                  | Terminal actions can read files, run scripts and write `/workspace/submission/eligible_trials.txt`. The required output is one trial ID per line, ordered by confidence. Blank lines and comments are allowed; duplicate IDs are deduplicated. | The effective tool and filesystem permissions inside a running agent sandbox.                                                                                                                  |
| Changing state           | Workspace files, the submission and processes can change. The shared data volume is mounted without a read-only flag. No order, referral or other care transaction is modeled.                                                                 | Whether source files can actually be changed under runtime user permissions, and whether any such change influences grading. A writable mount alone does not demonstrate a successful exploit. |
| Hidden information       | Gold labels and the grader belong to the scoring side. The main service does not mount the bootstrap-only scripts, raw cache or host tests directory in the inspected Compose file.                                                            | Effective isolation from grader files, labels, credentials and network-accessible answers. Container comments express an intended boundary; they do not prove it.                              |
| Initialization and reset | A bootstrap service stages the topic and candidate XML into the shared data volume before the main service starts. Cache-handling and download locks support staging.                                                                          | Fresh source and output state across repeated episodes. Bootstrap and cache reuse are not evidence that every reset is clean.                                                                  |
| Termination              | The agent budget is 3,600 seconds; verifier budget is 300 seconds. The terminal artifact is the submission file consumed by the evaluator.                                                                                                     | Harness behavior on normal completion, timeout, crash, missing output and repeated attempts. These lifecycle paths were not exercised here.                                                    |
| Evaluation               | The parser extracts identifiers, preserves their first occurrence, and filters out IDs outside the pool. The reward is 1 when every gold ID is among the first 50 retained predictions; otherwise it is 0.                                     | Clinical validity and completeness of the gold set. Precision and F1 are diagnostics; they do not gate this reward.                                                                            |

## Benchmark, reinforcement learning environment, or both?

**Both: a benchmark implemented through a reward-bearing episodic environment.** The benchmark role is comparison on defined tasks. The environment role is the interaction between observations, actions, changing state and a terminal reward. Sparse rewards and the absence of a built-in trainer do not remove that environment structure.

To use it for training, I would first verify resets, termination and isolation; repair the reward mismatch described in [the training-signal audit](reward-exploits.md); and connect a rollout and learning loop. A fixed reporting protocol and a private, held-out evaluation split would preserve the benchmark role. The split should separate related case families, not merely rename patient or trial identifiers.

This is a readiness distinction. An environment can support optimization before its reward is worth optimizing.

## What the two contrasting designs contribute

| Project and inspection scope                                                                                                                                                  | Relevant design                                                                                                                                                                                                                                                                                    | Implication for ChartAuth                                                                                                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **MedAgentBench.** Static reading of the [interaction implementation][medinteraction] and [evaluator dispatch][medeval] at commit `99260117137b09f04837a8c18d18a1107efa55ae`. | Structured EHR interactions use GET, POST and FINISH. In the inspected POST branch, JSON is parsed and a success response is returned without an HTTP POST in that branch. Evaluation separately dispatches to reference functions. Those separately supplied reference checks were not inspected. | Do not equate an action acknowledgment with persisted state. ChartAuth requires a saved record bound to the episode. This observation does not establish that every MedAgentBench task or reference check lacks persistence validation. |
| **HealthAdminBench.** Review of its [public repository][adminrepo] and [research description][adminpaper]; no comparative harness run.                                        | Browser-based administrative work is decomposed into exact state checks and judgment rubrics.                                                                                                                                                                                                      | Keep transaction facts deterministic. Reserve bounded judgment for support and usefulness that cannot be established by exact fields. A judge should not override a failed identity or transaction check.                               |

These are contrasting contracts, not a performance ranking. None of this inspection establishes the internal implementation of any organization beyond its cited public materials.

## The design consequence

The clinical-trial task grades a list. ChartAuth’s eligibility task grades a supported administrative result: the right patient, a response bound to the intended inquiry, a saved assessment and the next responsible team. A favorable answer is not the only valid completion; a documented unresolved issue can be the correct result.
